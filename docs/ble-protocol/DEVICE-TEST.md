## 0. 준비 — 코드 서명 팀 지정 (한 번만)

기기 빌드는 Apple 개발자 팀이 지정돼야 통과한다. 이 맥에는 여러 조직의 인증서가 섞여 있어
**어느 계정을 `com.dgitx.aiagentmonitor.mirror` 에 묶을지는 사람이 골라야 한다.**

```bash
cd ios && tuist generate     # --no-open 없이 실행하면 Xcode 가 열린다
```

무료 개발자 계정이면 설치본이 **7일 후 만료**되어 재설치가 필요하다. 유료(연 $99) 계정이면 1년이다.

- [ ] 주간 바는 주간 값이 있을 때만 나타난다
- [ ] 리셋 카운트다운이 1초마다 줄어들고 문구가 `약 X시간 Y분 Z초 남음` 이다
- [ ] 세션 목록이 최근 활동순으로 정렬되고 상대 시각(`10s ago`)이 갱신된다
- [ ] idle/dormant 행의 점 색과 상태 단어가 macOS 와 같다
- [ ] **두 화면을 나란히 놓고 비교했을 때 시각적으로 일치한다** ← 2단계 완료 판정

## 3-1. 페어링 확인 항목 (3단계 완료 판정)

3단계에서 6자리 코드 페어링과 챌린지-응답 재인증이 추가됐다. §1 의 BLE 공유를 처음
켠 상태(아직 페어링한 기기가 없는 상태)에서 시작한다.

- [ ] Mac Devices 탭에서 [페어링 시작] 을 누르면 6자리 코드가 뜨고, **120초 뒤
      화면에서 사라진다**(시도 5회를 다 쓰지 않았어도 만료된다)
- [ ] iPhone 에 코드 입력 화면이 뜬다. 6자리를 다 입력해야 확인 버튼이 활성화된다
- [ ] Mac 코드와 같은 값을 입력하면 화면이 닫히고 곧바로 미러링 화면이 흐르기
      시작한다
- [ ] 일부러 틀린 코드를 넣으면 남은 시도 횟수가 화면에 줄어들며(예: `4회 남음`),
      **5회를 전부 틀리면** 코드 입력 화면이 실패를 알리고 [페어링 시작] 을 다시
      눌러야 새 코드가 발급된다(스펙 5.1 — 창에는 소유자가 없고 시도 5회는 창
      전체가 공유한다)
- [ ] **앱을 껐다 켜도 코드 입력 없이 바로 연결된다.** 이 항목이 `TokenStore`
      (3단계 Task 6)의 Keychain 왕복을 실제로 검증하는 유일한 경로다 — 시뮬레이터
      유닛 테스트는 호스트 앱이 없는 로직 테스트 번들이라 `SecItemAdd` 가
      `errSecMissingEntitlement` 로 항상 실패해 막혀 있고(`testTokenStoreRoundTrip`
      은 `XCTSkip` 으로 건너뛴다), 이 항목이 통과해야 비로소 Keychain 저장·복원이
      실기기에서 실제로 동작함이 확인된다
- [ ] Mac 에서 페어링된 기기 중 하나만 골라 **해제** 를 누르면 그 iPhone 만 다시
      코드를 요구하고(재연결 시 AUTH→PROOF 가 거부됨), 다른 페어링된 기기(있다면)는
      계속 연결 상태를 유지한다
- [ ] Mac 에서 **전체 해제** 를 누르면 iPhone 이 다시 코드를 요구한다

## 4. 특히 주의할 항목 — 껐다 켜기 (1단계에서 확인됨, 전송 계층은 이번 단계에서 손대지 않았다)

`CBPeripheralManager` 에는 연결된 central 을 직접 끊는 API 가 없다. 그래서 공유를 끄면 GATT
서비스를 내리는 방식으로 "이 주변장치는 더 이상 없다"를 알린다. iOS 쪽은 그 신호를 받아
`didModifyServices` 에서 서비스를 다시 탐색하도록 구현해 뒀다(`BLEClient.swift:187`).

이 왕복은 1단계 실기기 확인에서 이미 검증됐다. 2단계는 전송 계층(`BLETransport`)을 건드리지
않았으므로 다시 확인할 필요는 없지만, 재연결 실패 증상은 여전히 아래와 같이 나타난다.

실패하면 이렇게 보인다: **iPhone은 「연결됨」인데 Mac은 연결된 기기 없음, 데이터 0바이트.**
그 경우 iPhone 앱을 재시작하면 복구된다. 증상을 보면 알려달라 — 진단 지점이 특정돼 있다.

## 5. 알아둘 것 — 이 앱은 로그를 남기지 않는다

README 는 `~/Library/Logs/AIMonitor/app.log` 에 로그가 쌓인다고 적고 있으나, 실제로는
`tracing-subscriber` 의존성도 초기화 코드도 없어 **모든 `tracing::error!` 출력이 버려진다.**
해당 디렉토리는 비어 있다.

BLE 와 무관한 기존 문제이며 이번 브랜치에서 고치지 않았다. 그래서 BLE 오류만은 로그가 아니라
Devices 패널에 직접 띄우도록 만들었다. 앱 전역 로깅을 살릴지는 별도 판단이 필요하다.

## 7. E2EE v2 확인 (2026-08-25 스펙)

4단계에서 페어링·재연결 트래픽이 통째로 암호화된다(스펙
`docs/superpowers/specs/2026-08-25-e2ee-protocol-v2-design.md`). §3-1 의 페어링 흐름
자체는 바뀌지 않지만, 그 아래를 흐르는 바이트가 전부 바뀌었고 v2 특유의 실패 방식이
새로 생겼다. 아래는 유닛 테스트(Rust 243개, iOS 135개, 전부 통과)로는 잡을 수 없는
항목만 추린 것이다 — 유닛 테스트가 잡는 것은 재검증하지 않는다.

### 7-1. 가장 먼저 볼 것 — Auth 응답이 notify 한 장에 안 들어갈 수 있다

v2 의 Auth 응답은 v1 보다 훨씬 길다. `AuthReply::to_json_bytes`(`src-tauri/src/ble/pairing.rs:109`)
가 실제로 만드는 JSON 길이를 hex 필드 길이(공개키 64자, 논스·토큰 32자 고정)로 그대로
계산하면:

| 응답 | 바이트 |
|---|---|
| `AwaitingCode2` | 149 |
| `Nonce2` | 134 |
| `Granted2` | 165 |

(`BLEClient.handleAuthReply` 의 주석과 Task 11 리뷰 기록은 `AwaitingCode2` 를
"148바이트"라 적어 두었다 — 직접 세어 보니 149바이트다. 코드 주석은 이 표에 맞춰
고쳤고, 리뷰 기록은 그때의 기록이라 그대로 둔다. 1바이트 차이라 결론에는 영향이
없지만, 숫자는 이 표가 맞는 쪽이다.
`Granted2` 가 셋 중 가장 크다는 점도 참고 — 기존 기록엔 셋 중 가장
작은 것처럼 적혀 있었는데, 봉인 프레임이 `counter(8) + ciphertext(44) + tag(16)` =
68바이트라 hex 로 136자나 되기 때문에 실제로는 반대다.)

맥은 이 응답들을 `macos.rs::notify_auth`(`src-tauri/src/ble/macos.rs:542`)로 보내는데,
**청킹이 없다** — 스냅샷(`offer_frame_to`)과 달리 `updateValue_forCharacteristic_onSubscribedCentrals`
를 한 번만 부른다(주석에 "요청 하나에 응답 하나"라고 이유가 적혀 있다). iOS 는 연결 시
185바이트를 요청하므로(Mac 쪽 테스트 픽스처 `max_notify_len: 185` 가 관측치를 반영한다)
위 세 값 모두 보통은 한 장에 들어간다. 하지만 이건 **실측이지 보장이 아니다** — MTU
협상이 낮게 끝나면(전파 환경, 기기, iOS 버전에 따라 달라질 수 있다) JSON 이 잘린 채
도착하고, `PairingClient.parse`(`ios/Sources/BLETransport/PairingClient.swift:54`)가
`nil` 을 돌려준다.

**증상은 페어링이 그냥 멈추는 것이다.** 화면이 아무 설명 없이 멈춘 것처럼 보인다.
이 앱은 로그 파일을 남기지 않으므로(§5), 이게 일어나면 볼 곳은 하나뿐이다:
`handleAuthReply`(`ios/Sources/BLETransport/BLEClient.swift:718`)가 파싱 실패 시
**바이트 수까지 찍는다**:

```
Auth 응답을 해석하지 못했습니다(N바이트)
```

- [ ] 페어링이 멈추면 Xcode 콘솔에서 이 로그부터 확인한다. `N` 이 위 표의 값보다
      작으면 MTU 잘림이 원인이다.

**근본 수정(Auth 특성도 청킹하기)은 이번 브랜치의 범위 밖이다.** Task 11 리뷰가 이미
"코드로는 확인할 수 없고 실기에서 멈추면 바이트 수 로그부터 봐야 한다"고 남겨 뒀다
— 이 항목이 그 대응이다. 실기에서 실제로 잘림이 재현되면, 청킹을 Auth 특성까지
확장하는 것이 이 문서가 아니라 별도 브랜치의 일이다.

### 7-2. 배포 순서

**맥을 먼저 올린다.** 맥은 v1·v2 를 모두 받지만(`pairing.rs` 의 `AuthRequest::Hello`
계열과 `Hello2` 계열이 나란히 존재한다) 클라이언트는 v2 만 말한다. 순서를 뒤집으면 —
새 아이폰 빌드를 먼저 배포하면 — 그 아이폰은 `HELLO2` 만 보낼 줄 아는데 옛 맥은
`Hello2` 를 모르는 `AuthRequest::Malformed` 로 해석해 페어링이 아예 시작되지 않는다.
사람이 보기엔 "새 아이폰만 페어링이 안 된다"로 보이고, 원인이 배포 순서라는 걸
알아채기 어렵다 — 그래서 순서 자체를 절차에 못 박아 둔다.

### 7-3. 확인 항목 (기존 페어링·재인증이 v2 에서도 그대로 되는지)

§3-1 의 흐름은 동일하다. v2 배포 후 아래를 다시 확인한다.

- [ ] 기존에 페어링된 아이폰(v1 토큰)이 맥 업데이트 후에도 그대로 붙는다
- [ ] 새 아이폰 빌드(v2)로 새로 페어링이 된다 — 코드 입력 → 곧바로 미러링 시작
- [ ] 재부팅 후 v2 로 자동 재인증된다(Keychain 토큰 → `AUTH2`/`PROOF2` 왕복)
- [ ] 맥에서 그 기기를 해제하면 즉시 끊기고, 다시 붙으려 하면 코드 화면이 뜬다
- [ ] 코드를 5번 틀리면 창이 닫히고, 그 뒤 시도는 전부 거부된다
- [ ] 창을 새로 열면 5회가 회복된다

### 7-4. 블루투스 껐다 켜기 — per-central 큐가 조용히 죽지 않는지

큐가 central 별로 바뀌면서(Task 8) 예전에는 "전체가 멈춤"으로 드러나던 문제가 이제는
**한 기기만 조용히 죽고 나머지는 멀쩡해 보이는** 형태로 나타날 수 있다. 코드 자체는
이를 막으려 하고 있다 — 전원이 꺼지면(`did_update_state`, `src-tauri/src/ble/macos.rs:237`)
구독과 큐를 통째로 비운다:

```rust
if !powered {
    let mut st = self.ivars().borrow_mut();
    st.subs.clear();
    st.queues.clear();
}
```

즉 전원이 꺼지는 순간 **포화돼 있던 큐도 함께 사라진다** — "포화된 채 paused 로 남은
큐가 되살아나지 않는다"는 브리핑의 우려는 이 코드가 있는 한 정확히는 일어나지 않는다.
다시 켜지면 서비스가 재게시되고(`publish()`), central 이 다시 구독하면 큐는 처음부터
새로 만들어진다(paused 상태를 물려받지 않는다).

**그래도 실기에서 봐야 하는 이유**는 남는다 — 이 클리어 로직이 실제로 항상 제때
호출되는지, 그리고 재게시 뒤 재구독·재전송이 실제 하드웨어에서 매끄럽게 이어지는지는
`CBPeripheralManager` 의 내부 동작이라 유닛 테스트로 확인할 수 없다. 특히 재게시
직후 `peripheralManagerIsReadyToUpdateSubscribers:` 가 (밀린 것이 없는데도) 오는지
안 오는지는 애플 문서에 명시돼 있지 않다 — 안 오는 경로가 있다면 그건 이 코드가
아니라 다른 원인일 것이므로 실기에서 재현해 알려줘야 한다.

- [ ] 아이폰 두 대를 페어링하고 둘 다 미러링이 흐르는 상태를 만든다
- [ ] 시스템 설정에서 블루투스를 껐다 켠다(앱의 BLE 공유 토글이 아니라 **시스템**
      블루투스다 — §4 의 껐다 켜기와 같은 종류지만, 이번엔 큐가 기기별이라는 점이
      다르다)
- [ ] **두 아이폰 모두** 미러링이 다시 흐르는지 확인한다 — 하나만 살아나고 다른
      하나는 「연결됨」인데 데이터가 없다면, 그 기기의 큐만 조용히 죽은 것이다

### 7-5. CBCentral identifier 회전

본딩하지 않은 peer 의 `CBCentral.identifier` 는 연결마다 바뀔 수 있다(macOS 가 central
을 식별하는 방식 — `src-tauri/src/ble/macos.rs:103` 주석 참고). 이 앱은 `CentralId`
하나로 구독·큐·인가를 전부 키잉하므로, 같은 아이폰이 재연결마다 다른 `CentralId` 로
보이면 겉으로는 "새 기기가 계속 나타나는" 것처럼 보인다.

- [ ] 같은 아이폰으로 연결·해제를 여러 번 반복한다(앱 재시작, 블루투스 토글 등으로)
- [ ] Mac Devices 탭의 페어링된 기기 목록에 같은 폰이 여러 항목으로 쌓이지 않는지
      확인한다. 쌓인다면 identifier 회전이 실제로 이 UI 에 영향을 주고 있다는 뜻이다

### 7-6. 특성별 구독 해제 — 가정 하나가 아직 실기로 확인되지 않았다

맥의 `did_unsubscribe`(`src-tauri/src/ble/macos.rs:283`)는 어떤 특성에서 구독이
해제됐는지(`_c: &CBCharacteristic` 인자)를 **보지 않는다** — 어느 특성이든 구독
해제 이벤트가 오면 그 central 의 큐를 **전부**(Auth 든 Snapshot 이든) 지운다. 지금은
무해하다. 큐에 실제로 쌓이는 건 Snapshot 뿐이고, iOS 쪽도 `setNotifyValue(false)` 를
일부러 부르지 않는다(`ios/Sources/BLETransport/BLEClient.swift:380` — 버전 불일치 시
`cancelPeripheralConnection` 으로 통째로 끊지, 특성 하나만 구독 해제하지 않는다).

즉 "iOS 가 특성 하나만 구독 해제하는 경우"는 지금 클라이언트 코드에 없다. 하지만 이건
**클라이언트가 그렇게 안 짜여 있다는 것**이지, CoreBluetooth 링크 계층에서 그런 일이
절대 일어나지 않는다는 보장은 아니다 — 이 문서가 아니라 실기 관찰로만 확인되는
가정이다.

- [ ] 정상적인 페어링·재연결·해제 과정에서 Auth 특성만 구독 해제되고 Snapshot 은
      살아 있는(또는 반대) 상황이 관찰되는지 눈여겨본다. 보통은 안 보여야 정상이다 —
      보인다면 이 가정이 깨진 것이므로 별도로 알린다

### 7-7. 평문이 나가지 않는지 실제로 본다

이 세 줄이 이 브랜치 전체의 완료 판정이다.

- [ ] **BLE**: `packetlogger`(Xcode Additional Tools)로 페어링을 한 번 캡처한다
- [ ] **네트워크(iroh/QUIC 미러 전송, `src-tauri/src/network/mod.rs`)**: `tcpdump` 로
      같은 페어링을 한 번 캡처한다. iroh 자체가 QUIC/TLS 로 전송을 감싸므로 캡처된
      패킷 자체는 이미 암호화돼 보일 것이다 — 그래도 캡처해서, 지금 확인하려는
      애플리케이션 계층 값(코드·토큰·스냅샷)이 어느 계층에서도 평문으로 새지
      않는다는 걸 별도로 증명해 둔다
- [ ] Auth 트래픽에 6자리 코드가 **나타나지 않는다** (v2 는 `HMAC(코드, transcript)`
      만 실어 보낸다 — 코드 자체는 맥 화면에만 뜬다)
- [ ] Auth 트래픽에 32자리 토큰이 **나타나지 않는다** (`Granted2` 는 토큰을 봉인
      프레임(`sealed`)에 담지, 평문 필드로 담지 않는다)
- [ ] Snapshot 특성 페이로드가 `{` 로 시작하지 **않는다** (평문 JSON 이 아니라
      `SealedChannel::seal` 이 만드는 `counter‖ciphertext‖tag` 봉인 프레임이다)

#### 실행 절차

위 체크리스트가 여태 한 번도 돌지 않은 이유는 "어떻게 돌리는가" 가 없어서다.
`verify-no-plaintext.sh` 가 그 자리를 채운다.

**이 검사의 함정은 항상 통과한다는 것이다.** 인터페이스를 잘못 골랐거나, 캡처
중에 페어링을 안 했거나, 필터가 트래픽을 다 걸러냈어도 "평문 없음" 은 성립한다.
그래서 스크립트는 먼저 양성 대조를 돌리고, 대조가 깨지면 나머지를 아예 돌리지
않는다. 그리고 코드를 넘기지 않으면 **exit 3** 으로 끝난다 — "통과" 와 "검사하지
않음" 을 종료 코드로 구분해서, 안 돈 검사가 통과로 기록되지 않게 한다.

찾는 값은 우리가 실제로 가진 값이다. 토큰은
`~/Library/Application Support/ai-agent-monitor/paired-peers.json` 의 32자 hex
이고, 평문 스냅샷의 서명은 `{"v":` 다 — `MirrorSnapshot` 이 `{ v, t, a }` 순서로
직렬화되기 때문이다(`src-tauri/src/ble/wire.rs:100`). 봉인 프레임은 hex ASCII 라
`{` 를 담지 않는다.

```bash
# 1) 네트워크(iroh) — 페어링 직전에 시작한다. en0 은 이 맥의 Wi-Fi.
sudo tcpdump -i en0 -s0 -w /tmp/aim-net.pcap
#    ...맥에서 [페어링 시작] → 폰으로 QR 스캔 → 코드 입력 → 미러 화면 확인...
#    Ctrl-C 로 멈춘다. 화면에 떴던 6자리 코드를 적어둔다.

# 2) 검사 (두 번째 인자는 화면에 떴던 코드 — 빼면 exit 3)
./docs/ble-protocol/verify-no-plaintext.sh /tmp/aim-net.pcap 482913
```

BLE 쪽은 `PacketLogger` 가 필요하고, 이건 Xcode 에 딸려 오지 않는다 —
developer.apple.com 의 **Additional Tools for Xcode** 를 따로 받아야 한다
(2026-08-26 기준 이 맥에는 설치돼 있지 않다). 설치 후 캡처해서 `.pklg` 를
같은 스크립트에 넘기면 된다. `strings` 기반이라 컨테이너 형식과 무관하게 돈다.

스크립트가 실제로 잡는지는 확인해 뒀다 — 랜덤 hex 캡처에 실제 토큰과
`{"v":2,...}` 를 심으면 두 항목 모두 FAIL 로 뜨고, 심지 않으면 통과한다.

### 7-8. 이 브랜치가 의도적으로 하지 않은 것

다음 사람이 "왜 안 됐지"를 찾아 헤매지 않도록 명시해 둔다.

- **Auth 특성 청킹.** §7-1 의 근본 수정. `notify_auth` 는 여전히 한 장으로 보낸다.
- **v1 지원 제거.** 맥은 v1·v2 를 계속 함께 받는다(§7-2). v1 을 걷어내는 건 이번
  범위가 아니다 — 그 결정은 아직 내려지지 않았다.
- **메시지 단위 전방 비밀성(래칫).** 스펙 §11 이 명시한 대로, 전방 비밀성은
  **연결 단위**다. 한 연결 안에서 세션 키가 유출되면 그 연결의 모든 메시지가
  열린다 — 재연결마다 키가 새로 나오는 것으로 이 용도엔 충분하다고 판단했을 뿐,
  메시지마다 키를 갈아 끼우는 래칫은 이 스펙에 없다.

## 8. LAN 공유 / mDNS 게시 (CYD, 브랜치 `feat/cyd-lan`)

> 추가 2026-08-26 · Task 5(mDNS 게시와 IP 표시)

여기 있는 항목은 **자동 테스트가 닿지 못하는 것들만** 모았다. 닿지 못하는 이유는
셋이다:

1. **mDNS 는 진짜 데몬과 멀티캐스트 망을 쓴다.** 유닛 테스트가 데몬을 띄우면
   `cargo test` 가 개발자의 망에 이 맥을 실제로 광고한다. 그래서 게시 여부를
   **결정하는 규칙**만 자동으로 보고(가짜 게시기), 레코드가 실제로 뿌려지는지는
   여기서 손으로 본다.
2. **`local_ipv4()` 는 그 맥의 라우팅 테이블에 달렸다.** 자동 테스트는 "값이 나오면
   IPv4 이고 루프백·링크로컬이 아니다"까지만 본다. 망이 없으면 `None` 이라 그
   테스트는 **아무것도 단정하지 않고 통과한다**(승인이 아니라 한계다).
3. **CYD 펌웨어는 이 저장소에 없다.** 서비스 타입 문자열은 언어를 건너뛰는
   계약이고, 그 계약이 지켜지는지는 하드웨어만 안다.

토글 UI 는 Task 6 이 만든다. 그 전에는 아래 §8-1 을 개발용으로만 확인할 수 있다.

### 8-1. 광고가 실제로 나가는가

```bash
pnpm tauri dev        # Devices 탭에서 LAN 공유를 켠다
dns-sd -B _aim._tcp local.                 # AIM-<호스트> 가 보여야 한다
dns-sd -L "AIM-<호스트>" _aim._tcp local.   # 포트 4320, TXT 는 v=2 하나뿐
```

- [ ] `dns-sd -B` 에 `AIM-<호스트>` 가 뜬다
- [ ] `dns-sd -L` 이 **4320** 을 말한다 (열려 있는 포트와 같은 값)
- [ ] TXT 에 `v=2` **말고는 아무것도 없다** — 6자리 코드나 토큰 조각이 보이면
      그 자리에서 멈춘다. 같은 WiFi 의 누구나 읽는 값이다
- [ ] 토글을 끄면 `dns-sd -B` 목록에서 **사라진다**(goodbye 가 나갔다는 뜻).
      TTL 만료를 기다려야 사라지면 `unregister` 가 빠진 것이다

### 8-2. 죽은 포트를 광고하지 않는가 — 이 태스크의 핵심

`BindFailed` 는 토글을 켠 채로 리스너만 없앤다. 광고가 토글에 매달려 있으면
여기서 **열리지 않은 포트가 계속 광고되고**, CYD 는 맥을 찾아내서 걸어갔다가 붙지
못한다 — 사람은 맥 패널에서 빨간 오류를 보지만 기기 쪽에는 알려 줄 화면이 없다.

```bash
nc -l 4320 &      # 포트를 미리 점유한다
# 그 상태에서 LAN 공유 토글을 켠다
dns-sd -B _aim._tcp local.
```

- [ ] 맥 패널에 "포트 4320 을(를) 열지 못했습니다…" 가 뜬다
- [ ] `dns-sd -B` 에 `AIM-<호스트>` 가 **뜨지 않는다**
- [ ] `nc` 를 끄고 토글을 껐다 켜면 그제서야 광고가 나타난다

### 8-3. 화면에 뜨는 IP 가 실제로 붙는 주소인가

수동 입력 경로다(mDNS 를 거르는 AP, 게스트 VLAN). Task 6 이 이 값을 패널에
띄운다.

```bash
route -n get default | grep interface   # 기본 경로의 인터페이스
ifconfig <그 인터페이스> | grep 'inet '  # 그 인터페이스의 IPv4
```

- [ ] 패널이 보여주는 주소가 **위 두 명령이 말하는 주소와 같다**
- [ ] 유선(썬더볼트 이더넷 등)으로 갈아 끼우고 다시 켜면 **유선 주소**가 나온다 —
      `en0`(WiFi)이 고정으로 나오면 인터페이스 이름이 어딘가에 박힌 것이다
- [ ] 전 구간 VPN 을 켜면 터널 주소가 나올 수 있다. **알려진 한계다** — 커널의 기본
      경로를 그대로 따르기 때문이고, 그 상태에서는 CYD 가 그 주소로 붙지 못한다.
      VPN 을 끄고 다시 본다

### 8-4. 윈도우 — 아직 손으로 돌려 보지 않았다

이 앱은 윈도우 MSI 도 낸다(`docs/release-notes/v1.5.0.md`). LAN 코드에는
`#[cfg(target_os)]` 게이트가 없으므로 게시와 주소 표시도 거기서 돈다.
서브프로세스(`ipconfig`/`scutil`)를 쓰지 않고 UDP 소켓과 `gethostname` 만
쓰는 이유가 그것이다 — 다만 **실제로 윈도우에서 돌려 본 사람은 아직 없다.**

- [ ] 윈도우에서 LAN 공유를 켜고, 주소 칸에 **설정 덤프 같은 문자열이 아니라**
      IPv4 하나가 뜨는지 본다
- [ ] Bonjour 가 설치된 윈도우라면 `dns-sd -B _aim._tcp local.` 로 같은 확인을 한다
- [ ] 컴퓨터 이름이 한글이면(한국 윈도우의 기본값) 인스턴스 이름이 깨지지 않고
      영숫자·하이픈으로 접혀 나오는지 본다

### 8-5. CYD 가 실제로 찾아내는가

- [ ] CYD 펌웨어가 `_aim._tcp.local.` 브라우즈로 맥을 찾는다
- [ ] 찾은 주소·포트로 붙어 `AUTH2`/`PROOF2` 를 통과하고 미러가 흐른다
- [ ] mDNS 를 거르는 망에서 주소를 손으로 넣어도 똑같이 붙는다
