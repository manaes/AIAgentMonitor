# E2EE 프로토콜 v2 설계

> 작성 2026-08-25
> 선행 스펙: `2026-08-25-shared-pairing-design.md` (공유 페어링)
> 이 스펙 위에 올라가는 것: `2026-08-25-cyd-client-design.md`

## 1. 왜 하는가

**지금 토큰이 평문으로 링크를 건넌다.**

`src-tauri/src/ble/macos.rs:275,286` 의 BLE 특성 권한은 `CBAttributePermissions::Readable` /
`Writeable` 이다 — `...EncryptionRequired` 가 아니다. 링크 계층 암호화가 없다. 그 위에서
페어링이 성공하면 `AuthReply::Granted` 가 `{"ok":true,"token":"<128비트 hex>"}` 를 그대로
내보낸다(`ble/pairing.rs:96`).

즉 페어링이 열려 있는 120초 동안 근처에서 스니핑하면 **장기 토큰을 통째로 가져간다.**
그 토큰이면 이후 언제든 재인증에 성공한다. 우리 설계가 "토큰은 발급 후 링크를 건너지
않는다"(챌린지-리스폰스)고 못박은 이유가 토큰이 장기 비밀이기 때문인데, **발급 순간만은
예외였다.** 6자리 코드도 `CODE:123456` 으로 평문이 나간다.

두 번째 이유는 새 전송이다. CYD 를 붙이려면 같은 WiFi 의 모든 기기가 닿는 LAN 전송이
생긴다. BLE 는 "10m 안에 있어야 한다"는 물리 제약이 방어의 일부였는데 LAN 에는 그것이
없다.

**따라서 이것은 새 기능이 아니라 이미 있는 결함의 수정이다.** 새 전송을 위해 필요한
것이기도 하지만, 새 전송이 없어도 해야 할 일이다.

## 2. 범위

- 전송 **독립** 계층으로 만든다. BLE·네트워크(iroh)·LAN 이 같은 코드를 쓴다.
- 적용 대상: 맥(Rust) + iOS(Swift). CYD 는 후속 스펙에서 이 위에 올라탄다.
- iroh 는 이미 QUIC TLS 로 암호화되지만 v2 를 **똑같이 적용한다** — 전송마다 다른 코드
  경로를 두지 않는 편이 안전하다. 중복 암호화 비용은 무시할 수준이다.
- 토큰 저장 형식(`paired-peers.json`)과 페어링 창 정책(TTL 120초, 창당 5회, 기본 꺼짐,
  `begin_pairing` 은 맥 사용자 제스처로만)은 **바뀌지 않는다.**

## 3. 암호 요소

| 역할 | 알고리즘 | 규격 |
|---|---|---|
| 키 합의 | X25519 | RFC 7748 |
| AEAD | ChaCha20-Poly1305 | RFC 8439 (키 32B, 논스 12B, 태그 16B) |
| KDF | HKDF-SHA256 | RFC 5869 |
| MAC | HMAC-SHA256 | 기존 v1 과 동일 |

AES-GCM 이 아니라 ChaCha20-Poly1305 를 고른 이유: 세 플랫폼 모두에서 하드웨어 가속
유무와 무관하게 성능이 일정하고, 타이밍 측면이 단순하며, ESP32 에서 단일 파일 라이브러리
(monocypher)로 해결되기 때문이다.

**의존성** (2026-08-25 기준 실제 해석되는 버전):

| 플랫폼 | X25519 | AEAD | HKDF |
|---|---|---|---|
| 맥 (Rust) | `x25519-dalek 3.0.0` | `chacha20poly1305 0.11.0` | `hkdf 0.13.0` |
| iOS (Swift) | `Curve25519.KeyAgreement` | `ChaChaPoly` | `HKDF` — 전부 CryptoKit 내장 |
| ESP32 (C) | monocypher (단일 파일) | 〃 | 〃 |

`curve25519-dalek 5.0.0` 은 iroh 때문에 이미 의존성 트리에 있다. `hmac 0.13.0` 과
`hkdf 0.13.0` 은 같은 RustCrypto 세대다.

ESP32 에서 mbedTLS 대신 monocypher 를 쓰는 이유: Arduino-ESP32 는 mbedTLS 가 미리
컴파일돼 있어 `MBEDTLS_CHACHAPOLY_C` 나 Curve25519 활성화 여부를 sdkconfig 로 바꿀 수
없다. monocypher 는 X25519 + ChaCha20-Poly1305 를 의존성 없이 한 파일로 제공한다.

## 4. 인코딩 규약

- 바이너리 값은 전부 **소문자 hex** 로 실린다(기존 토큰·논스·proof 와 동일).
- `token_bytes` 는 **토큰 hex 를 디코드한 원시 바이트**다. hex 문자열의 UTF-8 바이트가
  아니다 — v1 의 `docs/ble-protocol/golden/hmac-sample.json` 이 이미 못박은 규약을
  그대로 유지한다. 세 언어를 통틀어 가장 흔한 구현 실수라 골든 벡터로 묶는다.
- `transcript` = `cpk_bytes || spk_bytes` (32 + 32 = 64바이트). **항상 클라이언트 키가
  먼저다.** 역할과 무관하게 양쪽이 같은 순서로 만든다.
- 논스(핸드셰이크): 16바이트 난수 → 32 hex. v1 과 같은 길이다.

## 5. 핸드셰이크 — 페어링 (토큰 없음)

```
client → mac   HELLO2:<cpk>                       cpk = 클라이언트 임시 공개키 64 hex
mac    → client {"ok":false,"await":"code","v":2,
                 "epk":"<spk>","nonce":"<n>"}      spk = 맥 임시 공개키, n = 32 hex

               양쪽 계산:
                 ss   = X25519(임시 개인키, 상대 공개키)
                 k_pair = HKDF-SHA256(ikm = ss, salt = n_bytes,
                                      info = "aim-pair-v2", L = 32)

client → mac   CODE2:<cbind>
                 cbind = hex(HMAC-SHA256(key = utf8(6자리코드),
                                         msg = transcript))
mac    → client {"ok":true,"v":2,"sealed":"<hex>"}
                 sealed = 봉인 프레임(k_pair, counter=0, {"token":"<32 hex>"})
```

`sealed` 는 **7장이 정의한 봉인 프레임 전체**를 hex 로 담는다 — 즉 카운터 8바이트
접두를 포함한다. 여기서는 항상 0 이지만, 전송 경로마다 프레임 모양이 달라지지 않도록
같은 형식을 쓴다.

**임시 키쌍은 연결마다 새로 만든다.** 맥도 클라이언트도 재사용하지 않는다.

### 5.1 6자리 코드가 링크를 건너지 않는다

v1 은 `CODE:123456` 으로 코드를 그대로 보냈다. v2 는 코드를 **키로 써서** 두 임시 공개키를
MAC 한 값만 보낸다. 이것이 두 가지를 동시에 한다.

1. 코드 자체가 어느 방향으로도 링크에 나타나지 않는다.
2. **능동적 중간자를 막는다.** 중간자가 자기 임시 키를 끼워넣으면 `transcript` 가 달라져
   `cbind` 가 맞지 않는다. 중간자는 코드를 모르므로 올바른 `cbind` 를 만들 수 없다.

이것은 짧은 인증 문자열(short authenticated string) 방식이다. 코드의 엔트로피는 20비트
(1,000,000 분의 1)뿐이지만, **창당 5회라는 기존 예산이 온라인 추측을 5번으로 묶는다.**
이 예산은 절대 넓히지 않는다 — 이 논증 전체가 거기에 걸려 있다.

### 5.2 실패 처리

| 상황 | 응답 | 시도 예산 |
|---|---|---|
| `cbind` 불일치 | `{"ok":false,"left":N}` | **소모한다** (코드 추측이므로) |
| `cpk` 가 hex 가 아니거나 32바이트가 아님 | `{"ok":false}` | 소모하지 않는다 |
| `ss` 가 전부 0 (저차 점 공격) | `{"ok":false}` | 소모하지 않는다 |
| 창이 닫혀 있음 | `{"ok":false}` | — |

`cbind` 비교는 **상수 시간**으로 한다.

`ss` 전부 0 검사는 반드시 넣는다 — `x25519-dalek` 은 `SharedSecret::was_contributory()`
로 제공한다. 상대가 저차 점을 보내면 공유 비밀이 상수가 되어 키 합의가 무의미해진다.

## 6. 핸드셰이크 — 재연결 (토큰 있음)

```
client → mac   AUTH2:<cpk>
mac    → client {"ok":false,"v":2,"epk":"<spk>","nonce":"<n>"}

               양쪽 계산:
                 ss    = X25519(임시 개인키, 상대 공개키)
                 ikm   = ss || token_bytes            (32 + 16 = 48바이트)
                 k_s2c = HKDF-SHA256(ikm, salt = n_bytes, info = "aim-sess-v2-s2c")
                 k_c2s = HKDF-SHA256(ikm, salt = n_bytes, info = "aim-sess-v2-c2s")

client → mac   PROOF2:<proof>
                 proof = hex(HMAC-SHA256(key = token_bytes,
                                         msg = n_bytes || transcript))
mac    → client {"ok":true,"v":2}
```

v1 의 proof 는 `HMAC(token, nonce)` 였다. v2 는 `transcript` 를 붙여 **키 합의를 토큰에
묶는다** — 중간자가 임시 키를 바꿔치기하면 proof 가 맞지 않는다.

`ikm` 에 토큰을 넣는 이유: X25519 가 깨져도 토큰이 없으면 키를 못 만들고, 토큰이 새도
임시 개인키가 없으면 녹화된 트래픽을 못 푼다. 둘 다 필요하다.

맥은 저장된 토큰을 하나씩 시도해 일치하는 peer 를 찾는다(v1 과 동일). 불일치는
`{"ok":false}` 이고 **시도 예산을 소모하지 않는다** — 코드 추측이 아니기 때문이다.

### 6.1 페어링 직후의 키 전환

페어링(`5장`)이 성공하면 클라이언트는 방금 토큰을 받았다. 그 순간 **양쪽이 6장과 같은
방식으로** `k_s2c`/`k_c2s` 를 계산하고 그 키로 전환한다. 왕복이 더 필요 없다.

`k_pair` 는 **토큰 전달 한 건을 봉인하는 데만** 쓰이고 그 뒤로 쓰이지 않는다.

## 7. 데이터 단계

핸드셰이크 이후의 모든 페이로드는 봉인된다.

**방향마다 키가 다르고 카운터가 따로다.** 한쪽 방향의 카운터가 다른 방향과 섞일 여지를
없앤다.

```
AEAD 논스(12바이트) = [0,0,0,0] || counter.to_be_bytes()   (u64, 빅엔디안)
AAD                  = b"aim-v2"
봉인 프레임          = counter(8바이트 BE) || ciphertext || tag(16바이트)
```

카운터를 프레임에 실어 보내는 이유: BLE 청크 재조립은 순서가 어긋나면 프레임을 버린다
(`framing.rs` 의 `aborted`). 수신자가 자기 카운터만 세면 한 프레임만 유실돼도 영구히
어긋난다. 명시적으로 실으면 8바이트로 그 문제가 사라진다.

**재전송 방어**: 수신자는 방향별 `last_counter` 를 두고 `counter > last_counter` 인
프레임만 받는다. 같거나 작으면 세션을 즉시 끊는다.

카운터는 u64 이고 순환하지 않는다. 세션마다 키가 다르므로 0 에서 시작해도 (키, 논스)
쌍이 재사용되지 않는다 — **이것이 이 설계에서 가장 지키기 중요한 불변식이다.**

전송별 실림 방식:
- **BLE 스냅샷 특성**: 봉인 프레임 원시 바이트를 기존 청커에 그대로 넣는다.
- **LAN WebSocket**: 바이너리 프레임으로 그대로. 청킹 없음.
- **iroh 스트림**: 길이 접두 후 그대로.
- **제어 메시지(Auth 특성 등)**: JSON 안에 hex 로 넣는다(`"sealed"` 필드).

## 8. 버전 협상

| 동사 | 버전 |
|---|---|
| `HELLO` `CODE:` `AUTH` `PROOF:` | v1 |
| `HELLO2:` `CODE2:` `AUTH2:` `PROOF2:` | v2 |

- **맥은 전환 기간 동안 v1 과 v2 를 모두 받는다.** 이미 페어링된 아이폰이 갑자기 끊기지
  않는다.
- **클라이언트는 v2 만 말한다. 다운그레이드하지 않는다.** `Rejected` 를 받아도 v1 으로
  물러서지 않는다 — 물러서면 공격자가 v2 를 방해해 평문으로 끌어내릴 수 있다.
- 배포 순서: 맥 먼저(자동 업데이트), 그다음 클라이언트. 맥이 서버 역할이므로 이 순서가
  자연스럽다.
- v1 제거 시점은 이 스펙의 범위 밖이다. 제거할 때 별도 결정한다.

기존 파서는 모르는 동사를 전부 `Malformed` 로 처리하므로(`pairing.rs:parse_auth_request`),
**구버전 맥은 v2 클라이언트를 안전하게 거절한다.** 관대하게 받아주지 않는 기존 방침이
여기서 그대로 이득이 된다.

## 9. 코드 배치

```
src-tauri/src/crypto/mod.rs      새 모듈 — 전송 독립
  ├ ephemeral_keypair()          임시 키쌍 생성
  ├ derive_pair_key()            5장의 k_pair
  ├ derive_session_keys()        6장의 k_s2c / k_c2s
  ├ code_binding()               cbind 계산·검증(상수 시간)
  ├ session_proof()              v2 proof 계산·검증
  └ SealedChannel                방향별 키 + 카운터, seal()/open()
```

`AuthRequest` 는 v2 동사 다섯 개를 더 갖는다(`Hello2`/`Code2`/`Auth2`/`Proof2`, 그리고
기존 `Malformed`). `AuthReply` 는 v2 형태를 더 갖는다 — `AwaitingCode` 와 `Nonce` 는
임시 공개키를 함께 싣고, `Granted` 는 토큰을 평문 필드가 아니라 `sealed` 로 싣는다.
**v1 변형은 그대로 남는다**(8장의 전환 기간).

`PairingManager` 는 v2 동사 분기를 갖고 `crypto` 를 쓴다. 각 브리지(`ble`/`network`/`lan`)는
봉인·해제를 이 모듈에 위임한다 — **전송 코드에는 암호가 들어가지 않는다.**

`SealedChannel` 은 순수하다(난수·시계 의존 없음, 키와 카운터만). 그래야 골든 벡터로
고정할 수 있다.

## 10. 테스트

**골든 벡터** — `docs/ble-protocol/golden/e2ee-v2-sample.json`. 고정된 임시 개인키 두 개 +
고정된 논스 + 고정된 코드·토큰으로부터 `cbind`, `proof`, `k_s2c`, `k_c2s`, 봉인된 샘플
프레임까지 전부 기대값을 박는다. 세 언어가 같은 파일을 읽는다. v1 의 `hmac-sample.json` 이
이미 같은 역할을 하고 있고, 그 규약(원시 바이트 vs hex 문자열)을 여기서도 명시한다.

**반드시 테스트로 고정할 성질** — 이 프로젝트에서 반복해 확인된 "실제 동작이 테스트
사각지대에 있다" 패턴을 피하기 위해, 아래는 각각 순수 함수로 뽑아 테스트한다.

- 저차 점(전부 0 인 `ss`)을 거절한다
- `cbind` 불일치는 시도 예산을 소모하고, 형식 오류는 소모하지 않는다
- `proof` 불일치는 시도 예산을 소모하지 **않는다**
- 카운터가 같거나 작으면 세션을 끊는다(재전송 방어)
- 방향이 다른 키로 봉인한 프레임은 열리지 않는다
- 변조된 태그는 열리지 않는다
- 페어링 직후 키 전환이 양쪽에서 같은 키를 만든다

각 테스트는 **뮤테이션으로 검증한다** — 해당 검사를 지웠을 때 그 테스트가 실제로
빨개지는지 확인한다. 통과만 확인하는 것으로는 그 테스트가 무엇을 잡는지 알 수 없다.

**크로스 언어** — Rust 가 골든 벡터를 만들고(`UPDATE_GOLDEN=1`), Swift 와 C 가 읽어
대조한다. 기존 `ble::wire::tests::golden_*` 와 같은 방식이다.

## 11. 이 설계가 주지 않는 것

과장하지 않기 위해 명시한다.

- **메시지 단위 전방 비밀성은 없다.** 래칫이 없으므로 전방 비밀성은 **연결 단위**다. 한
  연결 안에서 세션 키가 유출되면 그 연결의 모든 메시지가 열린다. 이 용도에는 충분하다고
  판단했다.
- **엔드포인트가 털리면 아무것도 못 막는다.** ESP32 의 NVS 토큰은 플래시 암호화를 켜지
  않으면 평문이다. iOS Keychain 과 다르다. 대응은 기기별 해제(`peer_id`)뿐이다.
- **메타데이터는 보이지 않게 하지 않는다.** 페어링이 진행 중이라는 사실, 프레임 크기,
  전송 시각은 그대로 관측 가능하다.
- **첫 페어링에서 맥을 클라이언트에 인증하는 강도는 6자리 코드 그 자체다.** 20비트 +
  5회 예산. 그 이상이 필요하면 다른 설계가 필요하다.
- **BLE 링크 암호화(본딩)를 켜는 것은 이 스펙의 대안이 아니다.** 켜도 LAN 에는 도움이
  되지 않고, 애플리케이션 계층 하나로 세 전송을 덮는 편이 코드 경로가 하나다.

## 12. 유지되는 보안 제약

아래는 기존 스펙에서 그대로 가져오며 **완화하지 않는다.**

- 페어링 코드 TTL 120초
- 사용자가 연 창당 시도 5회 — **절대 넓히지 않는다.** 무차별 대입 논증과 5.1 의 중간자
  방어가 모두 여기에 걸려 있다
- 토큰은 128비트 소문자 hex
- 6자리 코드는 링크를 건너지 않는다 (v2 에서 양방향 모두로 강화됨)
- 인가되지 않은 상대는 스냅샷을 **0바이트** 받는다
- 토큰은 발급 이후 링크를 건너지 않는다 (v2 에서 발급 순간까지 봉인됨)
- BLE·네트워크·LAN 공유는 기본 꺼짐
- `begin_pairing` 은 맥 쪽 명시적 사용자 제스처로만 호출된다
